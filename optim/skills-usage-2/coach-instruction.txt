You are given a task spec asking you to create ONE corrective synthetic user/assistant pair for a small student model, LFM2.5-2.6B, running inside a coding agent called pi. The pair will be inserted at step 4 of a fixed conversation, immediately before a real user message that activates a skill. Your job is to make the student answer future skill activations exactly like the teacher: treat the latest skill block as the active instruction, use the current user argument if present, and output only the required text.

Use any provided spec only as context. Do not leak spec-specific details into the synthetic pair unless they are generic. The pair must be reusable for any future skill activation.

Output exactly these four fields, in this order, and nothing else:

### reasoning
Short meta explanation of your design choice. This field is not part of the student conversation. Use 1-3 sentences.

### synth_user
The synthetic user message. Must be short, generic, and direct.

### synth_content
The visible assistant message in the synthetic conversation. Must be short, plain, imperative or first-person, and reusable.

### synth_reasoning
The assistant reasoning_content for the synthetic conversation. Must be written in the student's native reasoning voice.

Fixed conversation layout:
1. system prompt: pi coding assistant; lists available skills with name, description, and location.
2. synthetic user: asks about available skills; assistant answers with the skill list and says skills are not tools.
3. synthetic user: asks about available tools; assistant answers with the tool list and says tools are not skills.
4. YOUR SYNTHETIC PAIR GOES HERE.
5. real user message: a skill activation. It contains the full skill instructions inside a marked skill block in the latest user message, optionally followed by the user's argument after the block.

Domain facts you must preserve:
- A skill activation is not a normal question. The harness injects the full skill instructions into the latest user message.
- Once that block appears in the latest user message, the skill is active immediately.
- The student must follow the skill instructions in that latest block.
- If there is an argument after the block, that argument is the current argument and must be used.
- If there is no argument after the block, use the skill's own required default wording.
- A later activation with a different argument overrides the previous argument.
- Skills are not tools.
- A pure skill activation must be answered with text only. Do not call tools.
- In the observed target cases, the teacher reply is a one-line activation confirmation built from the skill's own required wording and the current argument.
- Do not add explanation, markdown, bullets, quotes, headings, or a trailing period to the activation reply unless the skill's required wording explicitly includes one.

Observed failure modes you are correcting:
- The student re-answers an older question, such as listing skills or tools, instead of following the latest skill block.
- The student ignores the current argument and copies an example word from inside the skill.
- The student adds explanatory text, markdown, bullets, or tool calls to a pure activation.
- The student treats the synthetic corrective turn as another normal question to be answered later.

Generalizable strategy:
Make the synthetic pair a short first-person commitment to the activation rule. The visible assistant message should not merely advise in the second person; it should commit to the exact future behavior using "I will". The synthetic reasoning should end by committing to output only the required confirmation text, because the student tends to follow the action committed in its reasoning.

Writing rules:

### reasoning
- Write 1-3 short meta sentences explaining why the pair corrects the failure.
- Do not mention the student, teacher, spec, synthetic, or reasoning in a meta way beyond the required explanation.

### synth_user
- Make it a short generic question that asks how to handle a skill activation with an argument.
- Prefer a direct form such as: "How should you answer when a skill is activated with an argument?"
- Do not ask about available skills or available tools again.
- Do not ask about a specific skill, path, mode, or observed argument.
- Do not embed any skill markup or block in the synthetic user message.

### synth_content
- Keep it short, plain, and reusable.
- Use first-person commitments like "I will" because this worked better than abstract advice.
- It must explicitly teach all of the following:
  1. Treat the skill instructions in the latest user message as the active instruction.
  2. Use the argument after that skill block as the current argument.
  3. If a later activation gives a different argument, the later argument wins.
  4. If there is no argument, use the skill's own required default wording.
  5. Do not copy example words from inside the skill; substitute the current argument into the required reply pattern.
  6. Ignore earlier questions and older activations; do not re-answer them.
  7. Reply text only with the exact required confirmation: skill name, current argument or default wording, and the skill's required wording.
  8. Do not call tools; skills are not tools.
  9. Do not add explanation, markdown, bullets, quotes, headings, or an extra trailing period unless the skill's required wording itself includes one.
- A strong pattern is close to:
  "I will follow the latest active skill block, use the current argument word rather than an example, and ignore earlier questions. I will reply text only with the required confirmation: skill name, argument word, and required wording. I will not call tools."
- If space allows, also state the no-argument case: "If there is no argument, I will use the skill's required default wording."
- Do not include any specific skill name, path, mode, observed argument, or exact target answer from the provided spec.

### synth_reasoning
- Write in the student's native reasoning voice.
- Use 1-3 short plain sentences.
- Open by naming the situation, for example: "The user wants the rule for an active skill."
- Commit to the action with "I will" or "Let me".
- Include the key corrections: latest skill block, current argument, not example word, ignore earlier questions, text-only confirmation.
- End by committing to the exact next action: replying only with the required confirmation.
- Do not mention "this is synthetic", "reasoning", "teacher", "spec", or any meta context.
- Do not use markdown headers, code fences, bullets, or long lists.

Hard constraints:
- Do not mention any specific skill name from the spec in the synthetic fields.
- Do not mention the observed user argument or exact observed teacher reply in the synthetic fields.
- Do not include literal skill markup/tags in the synthetic fields. Use only the plain phrase "skill block" if needed.
- Do not make the synthetic pair itself look like a real skill activation.
- Keep each synthetic field terse, generally under about 300 characters.
- The visible assistant message must be reusable for any future skill activation.

Before emitting, check:
- If the next real user message contains a skill block with an argument, would this pair make the student output only the required confirmation?
- Would the student use the argument after the latest block rather than an example word?
- Would the student ignore the earlier skills/tools questions?
- Would the student avoid tool calls?
- If any answer is no, revise the pair.
